# Chapter 2.5: TypeScript for Go and Python Programmers

Just enough to make Chapter 3 make sense — not a full language book.
This chapter goes slower than the rest, on purpose. Nothing here goes
into the project; every snippet is a throwaway you can try in a
scratch file (`src/scratch.ts`, run with `node src/scratch.ts`, check
with `npm run typecheck`, delete when done). Every error message below
is real — copied from `tsc` 7.0.2, not paraphrased — because reading
the compiler's actual words is half of learning the language.

You know Go and Python. So instead of "what is a function," each
section asks: *what's different here?* Nine differences, plus a note on semicolons first. Then Chapter
3 starts building.

## 0. Semicolons: optional, with one catch

This book writes no semicolons at line ends. JavaScript inserts them
itself at each line break, just as Go's compiler does, and Python never
had them. So this works:

```ts
const a = 1
const b = 2
console.log(a + b) // 3
```

The catch: a line that *starts* with `[`, `(` or a backtick gets glued
onto the line above it, because a line ending in a value followed by
`[` looks like "index into that value":

```ts
const x = "tag"
[1, 2].forEach((n) => console.log(n))
```

JavaScript reads that as `const x = "tag"[1, 2].forEach(...)` and it
crashes:

```
[1, 2].forEach((n) => console.log(n))
       ^
```

The rule: **if a statement starts with `[`, `(` or a backtick, put a `;`
in front of it**:

```ts
const x = "tag"
;[1, 2].forEach((n) => console.log(n))
```

It comes up rarely, and this project never needs it. Lines *inside* a
list or a function call (after an opening `[`, `(` or a `,`) are fine.
The problem is only a new statement that starts with one of those
characters.

## 1. A type is a shape, not a name

In Go, two structs with identical fields are two different types. You
can't pass a `Location{X, Y}` where a `Point{X, Y}` is expected without
converting. The *name* is what matters.

TypeScript is the other way round. A type describes a *shape* — "has a
number called `x` and a number called `y`" — and anything with that
shape fits, whatever it was called when it was made:

```ts
interface Point {
  x: number
  y: number
}

function distance(p: Point): number {
  return Math.sqrt(p.x * p.x + p.y * p.y)
}

const spot = { x: 3, y: 4, label: "home" }
console.log(distance(spot)) // 5
```

`spot` was never declared as a `Point`. It has an extra field. It
still fits, because it has an `x` and a `y` that are numbers. This is
the same idea as Go's interfaces — "if it has the methods, it
satisfies the interface, no `implements` keyword" — applied to *every*
type, fields included. Python's duck typing, checked before the
program runs.

`interface` is the keyword for describing an object's shape. There's
also `type`, which can name *any* type, including ones that aren't
objects (you'll see it in section 4). For object shapes they're
interchangeable; this book uses `interface` for objects and `type` for
everything else.

One wrinkle. Write the object *directly* in the call — braces right
there — and the extra field is suddenly an error:

```ts
console.log(distance({ x: 1, y: 2, label: "inline" }))
```

```
error TS2353: Object literal may only specify known properties, and 'label' does not exist in type 'Point'.
```

Same shape as `spot`, opposite answer. The difference is what the
compiler can infer about your intent:

- `spot` has a life of its own. It's in a variable, it may be passed to
  five other functions, and `label` is presumably for one of them.
  Extra fields are none of `distance`'s business.
- The second object is born at the call and dies there. Nobody else
  will ever see it. So a field the parameter doesn't mention has no
  reason to exist — it's either dead weight or, far more likely, a
  mistake.

That second case is worth catching, and here's the example that shows
why:

```ts
interface Options {
  timeout?: number
}

function connect(o: Options): void { /* ... */ }

connect({ timeeout: 5000 })
```

Every field of `Options` is optional, so `{ timeeout: 5000 }` really
does satisfy the shape — `{}` would too. By shape rules alone this
compiles, and your timeout is silently ignored forever. Instead:

```
error TS2561: Object literal may only specify known properties, but 'timeeout' does not exist in type 'Options'. Did you mean to write 'timeout'?
```

The compiler even names the typo. This extra rule is called the
**excess property check**, and it fires only when an object literal is
written directly where a type is expected — as an argument, or
assigned to a typed variable:

```ts
const a: Point = { x: 1, y: 2, label: "nope" }
```

```
error TS2353: Object literal may only specify known properties, and 'label' does not exist in type 'Point'.
```

Give the object a name first and the check doesn't apply, because now
it's a value with its own life, not a literal. That's not a loophole to
feel clever about — it's the same distinction, and if you genuinely
want to pass an object with extras, naming it says so out loud.

## 2. Types are gone when the program runs

Chapter 2 showed this with a test that passed despite a type error.
Here's why it matters for a program that talks to a server.

`JSON.parse` turns text into a value. What type does it return? It
can't know — the text could be anything. Its declared return type is
actually `any`, which switches checking off (more on that below), so
this book always stores the result as `unknown` instead:

```ts
const raw: unknown = JSON.parse('{"size": 3630321}')
console.log(raw.size)
```

```
error TS18046: 'raw' is of type 'unknown'.
```

`unknown` means "there is a value here and I know nothing about it."
You can't read a field, call a method, or add one to it. You have to
*look first*:

```ts
if (typeof raw === "object" && raw !== null && "size" in raw && typeof raw.size === "number") {
  console.log(raw.size + 1) // 3630322
}
```

Inside that `if`, TypeScript has followed the checks and knows `raw`
has a numeric `size`. This is called **narrowing** — starting from a
wide type and using ordinary `if` checks to shrink it. It's how
TypeScript deals with the fact that the type is only ever a claim about
run-time data, never a guarantee. (The chain of `typeof` checks is
ugly, and Chapter 6 replaces it with `zod`, which does the same thing
declaratively. But this is what's underneath.)

There's a second option, `any`, which means "don't check anything":

```ts
const loose: any = JSON.parse('{"size": 3630321}')
console.log(loose.sizee.toFixed(2))
```

`tsc` says nothing. `sizee` is a typo. At run time:

```
TypeError: Cannot read properties of undefined (reading 'toFixed')
```

`any` switches TypeScript off for that value and everything derived
from it. You'll see it in older code and in quick scripts. In this
project it never appears; `unknown` plus a check is always the answer.
Think of it as `interface{}` in Go: you *can* hold anything, but you
have to type-assert before use — and TypeScript won't let you skip
that step, where Go will let you panic.

## 3. `undefined`, `null`, and the `?` family

Go has one "nothing" (`nil`) and Python has one (`None`). JavaScript
has two, for historical reasons:

- `undefined` — "was never set." A missing field, a missing argument,
  an array index past the end.
- `null` — "was set, deliberately, to nothing." What `JSON.parse`
  gives for the JSON value `null`.

You'll write `undefined` far more often. A field that might be absent
is marked with `?`:

```ts
interface Layer {
  digest: string
  size: number
  annotations?: Record<string, string>
}
```

`Record<string, string>` is "an object used as a dictionary: string
keys, string values" — Go's `map[string]string`. The `?` makes
`annotations` optional, which means its type is really "a record, *or*
`undefined`." Try to use it without checking:

```ts
function firstAnnotation(layer: Layer): string {
  return Object.keys(layer.annotations)[0]
}
```

```
error TS2769: ... Argument of type 'Record<string, string> | undefined' is not assignable to parameter of type 'object'.
error TS2322: Type 'string | undefined' is not assignable to type 'string'.
```

Two errors. The first: `annotations` might be `undefined`. The second:
even if it isn't, `[0]` on an array might be past the end — that's
`noUncheckedIndexedAccess` from Chapter 2 doing its job. Both are
fixed with `??`, which reads "or, if that's missing":

```ts
function firstAnnotation(layer: Layer): string {
  const keys = Object.keys(layer.annotations ?? {})
  return keys[0] ?? "(none)"
}
```

Two related operators you'll use constantly:

- `a ?? b` — `a`, unless it's `undefined`/`null`, then `b`.
- `a?.b` — `a.b`, unless `a` is `undefined`/`null`, then `undefined`
  (instead of crashing).

### `===`, and why never `==`

JavaScript has two equality operators. `===` compares what's there.
`==` converts one side to the other's type first, and the conversion
rules are their own small horror:

```
0 == ""              true      0 === ""             false
"5" == 5             true      "5" === 5            false
null == undefined    true      null === undefined   false
0 == false           true
"" == false          true
[] == false          true
null == 0            false     ← but null == undefined was true
```

That last line is the point: the rules aren't consistent even with each
other. Nobody memorises this; people just get bitten.

**Always write `===` and `!==`.** Go's `==` already behaves this way.
Python's sits in between — it converts across numbers (`1 == 1.0` is
true) but refuses `"5" == 5`.

TypeScript catches the obvious mistakes for you:

```ts
const s = "5"
const n = 5
console.log(s == n)
```

```
error TS2367: This comparison appears to be unintentional because the types 'string' and 'number' have no overlap.
```

— but only when it knows both types. Make one of them `any` and the
comparison compiles and prints `true`. Same lesson as section 2.

One `==` is idiomatic rather than a mistake: `x == null` is true for
both `null` and `undefined`, so it's the short way to ask "is there
nothing here?" This project writes `x === undefined`, because our own
code never produces `null` — but you'll meet `== null` in code that
handles JSON, and it's deliberate there.

And the thing you already met in Chapter 2's `main`:

```ts
const argv = ["alpine:3.20"]
const image = argv[0]
console.log(image.toUpperCase())
```

```
error TS18048: 'image' is possibly 'undefined'.
```

`argv[0]` might not exist. TypeScript won't let you pretend otherwise.
Every one of these errors is a `nil` dereference that didn't happen in
production.

## 4. "One of these": union types

Go has no direct way to say "this value is exactly one of these three
strings" — you'd use constants and hope. TypeScript does:

```ts
type Arch = "amd64" | "arm64" | "riscv64"

function goName(arch: Arch): string {
  return arch
}

goName("amd64")
goName("x86_64")
```

```
error TS2345: Argument of type '"x86_64"' is not assignable to parameter of type 'Arch'.
```

The `|` reads "or." This is what replaces `enum` (which Chapter 2
forbade), and it's better: the values are plain strings, so they read
naturally in JSON, in logs, and in tests.

It works for objects too, and this is where it earns its keep. Recall
from Chapter 1: ask for a tag, get back *either* an index *or* a
manifest. Write that down:

```ts
interface Manifest {
  mediaType: "application/vnd.oci.image.manifest.v1+json"
  layers: { digest: string; size: number }[]
}

interface Index {
  mediaType: "application/vnd.oci.image.index.v1+json"
  manifests: { digest: string; platform: { architecture: string } }[]
}

type ManifestOrIndex = Manifest | Index
```

Note `mediaType` isn't typed as `string` — it's typed as *one exact
string*. That's allowed, and it's the trick: the two shapes share a
field whose value tells you which one you're holding. Now try to use
`layers` without looking:

```ts
function describe(doc: ManifestOrIndex): string {
  return `${doc.layers.length} layers`
}
```

```
error TS2339: Property 'layers' does not exist on type 'ManifestOrIndex'.
  Property 'layers' does not exist on type 'Index'.
```

Correct — it might be an index. Look at `mediaType` first, and the
compiler follows along:

```ts
function describe(doc: ManifestOrIndex): string {
  switch (doc.mediaType) {
    case "application/vnd.oci.image.manifest.v1+json":
      return `${doc.layers.length} layers`
    case "application/vnd.oci.image.index.v1+json":
      return `${doc.manifests.length} platforms`
  }
}
```

Inside the first `case`, `doc` is a `Manifest` and `.layers` is fine.
Inside the second, it's an `Index`. Delete the second `case` and:

```
error TS2366: Function lacks ending return statement and return type does not include 'undefined'.
```

— the compiler noticed a shape you forgot to handle. Add a third shape
to the union next year, and every `switch` that doesn't handle it
fails to compile. That is the safety Go's type switches don't give
you, and the pattern Chapter 6 uses to tell index from manifest.

## 5. Errors: `throw`, `catch`, and your own error types

TypeScript uses exceptions, like Python, not returned errors, like Go.
`throw` anything; `catch` it with `try`. The one rule this project
follows: **only throw `Error` objects**, and make your own kinds by
extending `Error`:

```ts
class DigestMismatchError extends Error {
  readonly expected: string
  readonly actual: string

  constructor(expected: string, actual: string) {
    super(`digest mismatch: expected ${expected}, got ${actual}`)
    this.name = "DigestMismatchError"
    this.expected = expected
    this.actual = actual
  }
}

function verify(expected: string, actual: string): void {
  if (expected !== actual) {
    throw new DigestMismatchError(expected, actual)
  }
}
```

`super(...)` calls `Error`'s own constructor with the message. Setting
`this.name` makes stack traces say `DigestMismatchError` instead of
`Error`. `readonly` is Go's "no setter" — assign once in the
constructor, never again.

Now catch it. What type is the caught value?

```ts
try {
  verify("sha256:aaa", "sha256:bbb")
} catch (err) {
  console.log(err.message)
}
```

```
error TS18046: 'err' is of type 'unknown'.
```

`unknown` — because *anything* can be thrown, so the compiler
honestly doesn't know. Same rule as section 2: look first.
`instanceof` is the check:

```ts
} catch (err) {
  if (err instanceof DigestMismatchError) {
    console.log(err.name, "->", err.expected, "vs", err.actual)
  } else {
    throw err
  }
}
```

```
DigestMismatchError -> sha256:aaa vs sha256:bbb
```

Inside the `if`, `err` is narrowed to `DigestMismatchError` and its
fields are available. Anything you didn't expect gets re-thrown rather
than swallowed — the equivalent of Go's `errors.As` plus "return the
error if it's not the one you handle."

## 6. `async`/`await`: what's actually different from Go

This is the one that trips Go programmers most, so it gets the longest
section.

In Go, `go f()` starts `f` on another goroutine and the runtime may run
it *in parallel* on another CPU. In Node, **there is one thread running
your code**. Nothing you write runs at the same time as anything else
you write. What Node does have is a way to say "this will take a while
— go do something else and come back when it's ready." That's
`async`/`await`, and it's much closer to Python's `asyncio` than to
goroutines.

A function marked `async` returns a **Promise** — a box that will hold
a value later. `await` opens the box, pausing *this function only*
until the value arrives; other work keeps going in the meantime.

```ts
function sleep(ms: number): Promise<void> {
  return new Promise((resolve) => setTimeout(resolve, ms))
}

async function download(name: string, ms: number): Promise<string> {
  console.log(`start ${name}`)
  await sleep(ms)
  console.log(`done  ${name}`)
  return `${name}: ${ms}ms`
}
```

(`sleep` wraps Node's `setTimeout` — "call this function after `ms`
milliseconds" — into a Promise so it can be awaited. You'll write this
helper once in Chapter 8 and never think about it again. `Promise<void>`
is "a promise of nothing," `Promise<string>` "a promise of a string";
the angle brackets are the same idea as Go's `chan string`.)

One at a time:

```ts
async function oneAtATime(): Promise<void> {
  const t0 = Date.now()
  const a = await download("layer-1", 300)
  const b = await download("layer-2", 300)
  console.log([a, b], `${Date.now() - t0}ms total`)
}
```

```
start layer-1
done  layer-1
start layer-2
done  layer-2
[ 'layer-1: 300ms', 'layer-2: 300ms' ] 607ms total
```

600 ms, because each `await` waited for the previous download before
starting the next. Now start both, *then* wait:

```ts
async function allAtOnce(): Promise<void> {
  const t0 = Date.now()
  const results = await Promise.all([download("layer-1", 300), download("layer-2", 300)])
  console.log(results, `${Date.now() - t0}ms total`)
}
```

```
start layer-1
start layer-2
done  layer-1
done  layer-2
[ 'layer-1: 300ms', 'layer-2: 300ms' ] 302ms total
```

300 ms. Calling `download(...)` *without* `await` starts it and hands
back the box immediately. `Promise.all` takes a list of boxes and gives
you one box that opens when all of them have. That's `sync.WaitGroup`
plus collecting the results, in one line — and it's how Chapter 8
downloads every layer at once.

Two things worth knowing now:

**Only `async` functions can `await`.** If you need to wait inside an
ordinary function, make it `async` — and then its callers must `await`
it, and so on up. This "spreads" through a codebase. That's normal and
expected; most of this project's functions will be `async`, because
most of them wait on the network or the disk.

**Forgetting `await` is the classic bug**, and TypeScript catches most
of it:

```ts
async function fetchSize(): Promise<number> {
  return 3630321
}

const size = fetchSize()
console.log(size + 1)
```

```
error TS2365: Operator '+' cannot be applied to types 'Promise<number>' and '1'.
```

Without the type check, this prints `[object Promise]1`. With it, the
compiler tells you you're holding a box, not a number.

Finally: when something inside an `async` function throws, the Promise
"rejects," and `await`ing it re-throws at the `await`. So `try`/`catch`
around an `await` works exactly like `try`/`catch` around a normal call.
No special error-handling story to learn.

## 7. Modules, `export`, and `import type`

A file is a module. Nothing leaves it unless marked `export`; nothing
enters unless `import`ed. You saw both in Chapter 2. One extra rule,
enforced by `verbatimModuleSyntax` from the tsconfig:

```ts
// types.ts
export interface Reference {
  readonly registry: string
  readonly repository: string
  readonly tag: string
}
export function parse(name: string): Reference { /* ... */ }

// use.ts
import { Reference, parse } from "./types.ts"
```

```
error TS1484: 'Reference' is a type and must be imported using a type-only import when 'verbatimModuleSyntax' is enabled.
```

`Reference` is a type. Types are deleted before the program runs
(section 2). Node, doing that deletion, needs to know *which* imports
to drop, so you have to say:

```ts
import { type Reference, parse } from "./types.ts"
```

`type` in front of the name means "this one's a type, delete it."
`parse` is a real function and stays. If *everything* you import from a
file is a type, write `import type { ... } from`. The compiler tells
you every time you forget, so there's nothing to memorise.

And since `Reference` is all `readonly`:

```ts
const ref: Reference = parse("alpine")
ref.tag = "3.20"
```

```
error TS2540: Cannot assign to 'tag' because it is a read-only property.
```

Most of this project's data types will be `readonly` throughout. A
value that can't change after it's made is a value you never have to
wonder about.

## 8. Classes and interfaces, the way this book uses them

You could write this whole tool with functions and plain objects. We'll
use a few classes, for one specific reason: a class can hold something
it was *given* — an HTTP client, a clock, a folder path — and every
method then uses it. That's the shape that makes faking easy in tests.
Here's the pattern in miniature, with a clock:

```ts
interface Clock {
  now(): number
}

class SystemClock implements Clock {
  now(): number {
    return Date.now()
  }
}

class FakeClock implements Clock {
  private current = 0

  now(): number {
    return this.current
  }

  advance(ms: number): void {
    this.current += ms
  }
}

class Stopwatch {
  private readonly clock: Clock
  private started = 0

  constructor(clock: Clock) {
    this.clock = clock
  }

  start(): void {
    this.started = this.clock.now()
  }

  elapsed(): number {
    return this.clock.now() - this.started
  }
}
```

Read it top to bottom:

- `interface Clock` describes what a clock *can do*, not how. This is a
  Go interface with one method.
- `implements Clock` on a class is optional (section 1 — shape is what
  matters), but it makes the compiler check that the class really does
  have the method, right there, rather than at the first place it's
  used. Cheap and worth it.
- `private` means only code inside the class can touch the field. Try
  `fake.current` from outside and:

  ```
  error TS2341: Property 'current' is private and only accessible within class 'FakeClock'.
  ```

  Go does this with lowercase names; TypeScript with a keyword.
- `Stopwatch` doesn't make its own clock. It's *given* one in the
  constructor and stores it. So in a test:

  ```ts
  const fake = new FakeClock()
  const watch = new Stopwatch(fake)
  watch.start()
  fake.advance(250)
  console.log(watch.elapsed()) // 250
  ```

  No real time passed. That's the entire trick behind every fake in
  this book: **a class asks for what it needs instead of making it, so
  a test can hand it a pretend version.** The idea has a name —
  depending on an abstraction (the `Clock` interface) instead of a
  concrete thing (`Date.now`) — and it'll be named again in Chapter 4
  when the thing being faked is the network.

One small thing you *can't* do, because of `erasableSyntaxOnly`: the
shorthand `constructor(private readonly clock: Clock) {}` that declares
and assigns a field in one go. It's a TypeScript-only feature that
isn't just a label, so Node can't strip it. The three-line version
above is what we write.

## 9. Generics, briefly

You've already used them: `Promise<string>`, `Record<string, string>`,
`Map<string, number>`. Angle brackets are "a type with a hole in it,
and here's what fills the hole." Go got the same feature in 1.18 with
the same square-bracket idea.

Writing your own:

```ts
function first<T>(items: T[]): T | undefined {
  return items[0]
}

const n = first([1, 2, 3])   // n: number | undefined
const s = first(["a", "b"])  // s: string | undefined
```

`T` is filled in from whatever you pass. Chapter 8 writes one generic
function — the "run at most N of these at a time" limiter — and
explains it fully then. Until then, you only need to read them.

## What you should now be able to answer

Try to answer each one in your own words first. Then open the answer to check.

**1. Why does an object with extra fields fit a type that doesn't mention them, and why is the same object rejected when written directly in the call?**

<details>
<summary>Answer</summary>

A type is a *shape*: anything with the required fields fits, and extra fields are ignored. An object in a variable may be used elsewhere, so its extras are none of this function's business. An object written directly in the call exists only there, so a field the type doesn't mention is almost always a mistake, like the typo `timeeout`. The compiler's *excess property check* catches it in that case only.

</details>

**2. What's the difference between `unknown` and `any`, and which one does `JSON.parse` deserve?**

<details>
<summary>Answer</summary>

`unknown` means "a value I know nothing about": you can't use it until you've checked what it is (narrowing). `any` switches type checking *off* for that value and everything made from it, so typos compile and crash at run time. `JSON.parse` is declared as returning `any`, but it deserves `unknown`. Store its result as `const raw: unknown = JSON.parse(...)` and check before use.

</details>

**3. What does `?` after a field name mean? What do `??` and `?.` do?**

<details>
<summary>Answer</summary>

`field?:` means the field is optional: it may be missing, so its type includes `undefined`. `a ?? b` gives `a`, unless `a` is `undefined` or `null`, and then gives `b`. `a?.b` gives `a.b`, unless `a` is `undefined` or `null`, and then gives `undefined` instead of crashing.

</details>

**4. Why `===` and never `==`? What's the one exception?**

<details>
<summary>Answer</summary>

`==` converts one side to the other's type before comparing, and the conversion rules are inconsistent (`0 == ""` is true, `null == 0` is false). `===` compares what's actually there, like Go's `==`. The exception is `x == null`, which is the short, deliberate way to ask "is this `null` *or* `undefined`?". This project writes `=== undefined` instead, because our code never produces `null`.

</details>

**5. Semicolons are optional. When does leaving one out break the code?**

<details>
<summary>Answer</summary>

When a new statement *starts* with `[`, `(` or a backtick. JavaScript then glues it onto the line above (for example, `"tag"[1, 2]`). Put a `;` at the start of such a line.

</details>

**6. How do you say "one of these three strings"? How does a `switch` on a shared field let the compiler know which shape you hold?**

<details>
<summary>Answer</summary>

Write a union of exact strings: `type Arch = "amd64" | "arm64" | "riscv64"`. For objects, give every shape a shared field typed as one exact string (like `mediaType` or `kind`). In each `case` of a `switch` on that field, the compiler knows which shape you have, so its own fields are allowed. Leave a shape unhandled and the function stops compiling.

</details>

**7. Why is a caught error `unknown`, and how do you get at its fields?**

<details>
<summary>Answer</summary>

Because JavaScript lets you `throw` *anything*, not just `Error` objects, so the compiler can't know what arrives. Check it with `instanceof YourError`: inside that `if`, it's narrowed and its fields are available. Re-throw anything you don't recognise.

</details>

**8. Does `async` code in Node run in parallel? What does `await` pause? What's the difference between two `await`s in a row and `Promise.all`?**

<details>
<summary>Answer</summary>

No. One thread runs all your code, so nothing you write runs at the same time as anything else. `await` pauses *only the function it's in* until the Promise has its value, and other work carries on meanwhile. Two `await`s in a row run one after the other (300 ms + 300 ms = 600 ms). `Promise.all` starts both first, then waits for both (about 300 ms).

</details>

**9. Why must some imports say `type`?**

<details>
<summary>Answer</summary>

Types are deleted before the program runs. With `verbatimModuleSyntax` on, an import that is only a type must be marked `type`, so the deleting step knows to drop it. Otherwise Node would try to import a name that doesn't exist at run time.

</details>

**10. Why does `Stopwatch` take a `Clock` instead of calling `Date.now()`?**

<details>
<summary>Answer</summary>

So it can be handed a pretend clock in a test and time can be moved forward by hand, with no real waiting. `Stopwatch` depends on a description (the `Clock` interface) rather than one concrete thing (`Date.now`). That's dependency inversion, the trick behind every fake in this book.

</details>
